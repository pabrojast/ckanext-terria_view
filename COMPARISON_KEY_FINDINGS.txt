4. SLD PROCESSING: ⚠️ MOSTLY COMPATIBLE, SOME DIFFERENCES
================================================================================

IDENTICAL COG Processing:
  1. Parse ColorMapEntry elements
  2. Extract: quantity, color, label, opacity
  3. Convert hex colors to RGB/RGBA strings
  4. Create colors array: [[quantity_val, "rgb(...)"]]
  5. Filter transparent (opacity 0) as nodata
  6. Create legend items with title and color

  Plugin: sld_processor.py lines 546-620 (process_cog_sld)
  DAG:    lines 120-168 (in process_sld_styles)

IDENTICAL SHP Processing:
  1. Parse Rule elements from SLD
  2. Skip ElseFilter rules (fallback conditions)
  3. Extract: property_name, color, label
  4. Determine if data is categorical or numeric
  5. For categorical: mapType="enum" with enumColors
  6. For numeric: mapType="bin" with binMaximums/binColors
  7. Create legend items

  Plugin: sld_processor.py lines 693+ (process_shp_sld)
  DAG:    lines 170-305 (in process_sld_styles)

DIFFERENCES IN COG:
  
  Plugin EXTRA: Gradient enhancement (line 619 of sld_processor.py)
    if len(colors) >= 2 and interpolation_type == "linear":
        colors = self._enhance_color_gradient(colors, interpolation_type)
  
  DAG: No gradient enhancement
  
  Impact: Plugin may produce smoother color transitions for continuous colormaps
  
  Plugin EXTRA: Explicit interpolation type detection
    color_map_type = color_map.get('type', '').strip().lower()
    if color_map_type == 'ramp':
        interpolation_type = "linear"
  
  DAG: No interpolation type awareness
  
  Impact: Plugin can differentiate between "ramp" and "intervals" type colormaps

SHARED DIFFERENCES FROM IDEAL:
  ⚠️ Both may miss ColorMapEntry with incomplete attributes
  ⚠️ Both depend on correct SLD namespace declarations

5. CUSTOM CONFIGURATION: ✅ 100% IDENTICAL
================================================================================

Both support Terria sharing format: URL#share=g-{gist_id}

Plugin: _apply_custom_config() lines 233-278
DAG:    lines 612-665

Process:
  1. Parse URL fragment: fragment = urllib.parse.urlparse(custom_config).fragment
  2. If fragment.startswith('share='):
       → Extract gist_id from "share=g-{id}"
       → Fetch from GitHub: https://gist.githubusercontent.com/pabrojast/{id}/raw/
  3. If fragment.startswith('start='):
       → URL decode the start parameter
  4. Parse JSON
  5. Extract initSources
  6. Apply to elemento:
       - custom_data['initSources'][0]['models'][key]['legends']
       - custom_data['initSources'][0]['models'][key]['styles']
       - custom_data['initSources'][0]['models'][key]['renderOptions']

11. CONCLUSION
================================================================================

The two systems are FUNDAMENTALLY COMPATIBLE:
  • Same JSON output structure
  • Same resource fields and values
  • Same SLD processing logic (mostly)
  • Same custom config handling
  • Same org metadata display

But they have IMPORTANT DIFFERENCES:
  • Plugin: Class-based, cached, on-demand, HTTP API
  • DAG: Function-based, batch-processed, scheduled, file upload
  • Plugin: More sophisticated SLD with gradients
  • DAG: Simpler SLD, fallback styling, CKAN integration
  • Plugin: Modular output option
  • DAG: Flat hierarchy

Migration between them is LOW-RISK IF:
  1. You test COG gradient rendering (visual verification)
  2. You verify SHP categorical classification (test with sample data)
  3. You handle deployment differences (DAG upload vs plugin API)
  4. You adjust for caching behavior (plugin: faster but stale; DAG: slower but current)
